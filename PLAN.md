# NotifFilter — Android notification filter

Plan drafted 2026-07-29. All package versions verified against the npm registry on this date; re-verify at scaffold time.

## 1. Product

An Android app that intercepts notifications **before they are shown** and decides
per-notification whether to cancel them, based on user rules:

- Scope: all apps, or a selectable set of apps.
- Matching: Java regex against notification content (title/text).
- Actions: allow / deny, plus a global default policy (allowlist vs denylist mode).
- Cancelled notifications never reach the user; both shown and blocked notifications are
  logged in a unified, clearable history so the user can verify rules work correctly.

Android-only. Offline-first, no network, no analytics.

## 2. Architecture — the one decision that matters

**Filtering happens in Kotlin, inside a `NotificationListenerService`, not in JavaScript.**

Reasons:
- The listener service is bound by the Android system; it runs even when the app
  process is killed. There is no reliable way to wake a JS bundle per notification
  with low latency and low battery cost.
- Regex matching in `java.util.regex` is fast and testable as pure JVM code.
- JS stays responsible for what it's good at: the rule-management UI.

Consequences:
- Rules and settings live in **native storage** (`SharedPreferences`, JSON blob),
  written through a Kotlin `RuleStore` owned by our Expo module. The JS side keeps a
  zustand cache for UI reactivity but is never the source of truth. No MMKV/AsyncStorage
  duplication, no sync drift.
- The blocked-notification log is written natively (SQLite) and read by JS.

## 3. Rule model & evaluation semantics (pinned)

```ts
type Rule = {
  id: string;                    // uuid
  label?: string;                // optional user-facing name
  enabled: boolean;
  scope: { kind: 'all' } | { kind: 'packages'; packages: string[] };
  field: 'title' | 'text' | 'any';   // 'any' = title + text + expanded text
  pattern: string;               // Java regex
  caseInsensitive: boolean;
  action: 'allow' | 'deny';
  updatedAt: number;
};

type Settings = {
  defaultPolicy: 'allow' | 'block';  // denylist mode / allowlist mode
  filterOngoing: boolean;            // default false
  logSize: number;                   // default 500
  theme: 'system' | 'light' | 'dark';
};
```

Per-notification evaluation (all in Kotlin, on the main thread — NLS callbacks are
main-thread on API 24+; matching is fast enough, otherwise offload to a single handler):

1. Extract candidate rules: `enabled && (scope == all || packages contains sbn.packageName)`.
2. Build match targets from `StatusBarNotification`: `EXTRA_TITLE`, `EXTRA_TEXT`,
   `EXTRA_SUB_TEXT`, `EXTRA_INFO_TEXT`, `EXTRA_SUMMARY_TEXT`, `EXTRA_TEXT_LINES`,
   `EXTRA_BIG_TEXT`. Per-field or concatenated per `rule.field`. Cap input at ~4 KB
   (regex DoS guard).
3. **Deny wins.** Any matching deny rule → cancel.
4. Else if `defaultPolicy == 'block'`: require a matching allow rule; none → cancel.
5. Cancel path: `cancelNotification(sbn.key)` + insert into blocked log (app, title
   preview, matched rule id+pattern, timestamp, postTime).

### Guardrails
- **Ongoing/foreground-service notifications** (media, navigation, calls): skipped by
  default (`filterOngoing=false`). Cancelling those can stop playback or kill FGS UX;
  users opt in knowingly.
- **Android 15+ OTP redaction:** the system hands us `"sensitive notification content hidden"`
  for OTP notifications to non-trusted listeners. Content rules can't match what we can't
  see — package-scope rules still work. State this plainly in the app's help text; it is a
  platform privacy feature, not a bug.
- **Grouped notifications:** cancelling children doesn't always clear the summary; v1
  cancels matched items only. Auto-collapsing empty groups = later QoL.
- Precompile `Pattern` objects once per rules-write, cache in memory in the service.

## 4. Native module surface (Expo Module, Kotlin)

```
isListenerEnabled(): boolean            // NotificationManagerCompat.getEnabledListenerPackages
openNotificationAccessSettings()        // ACTION_NOTIFICATION_LISTENER_SETTINGS
getRules(): string                      // JSON from RuleStore
saveRules(json: string)                 // atomic write + recompile + notify service
getSettings(): string / saveSettings(json)
listInstalledApps(query?): [{package, label}]   // launcher apps via <queries>; see §5
getAppIcon(package): string             // content:// or base64, cached
testPattern(pattern, caseInsensitive, samples: {title?, text?}): {matches, field}
getBlockedEntries(limit, beforeTs?): [...]      // SQLite, newest first
clearBlockedLog()
restoreEntry(id): boolean               // re-post a copy via NotificationManager
postTestNotification(title, text)       // built-in test harness
Events: onBlocked(entry), onListenerConnectionChanged(connected)
```

`testPattern` runs in the **same engine as the service** — the rule editor's live
preview is guaranteed to match real behavior (no JS/Java regex divergence).

## 5. Permissions & manifest (Android 16)

- Service declaration (per official docs):
  `exported="false"`, `permission="android.permission.BIND_NOTIFICATION_LISTENER_SERVICE"`,
  intent-filter `android.service.notification.NotificationListenerService`,
  meta-data `default_filter_types = conversations|alerting|silent|ongoing`
  (receive all types; skip ongoing in code unless enabled).
- Notification access is a **special permission**: granted only by the user in system
  Settings. Onboarding screens deep-link there and poll `isListenerEnabled()` on resume.
  The system rebinds enabled listeners automatically after reboot/app updates — no boot
  receiver needed.
- **App inventory:** two options, decided by distribution question (§9):
  - `QUERY_ALL_PACKAGES` — full list, needs Play declaration justification.
  - `<queries>` with MAIN/LAUNCHER intent — Play-safe, misses headless apps.
- `POST_NOTIFICATIONS` (runtime, Android 13+) — only needed for the restore feature.
- Optionally strip `INTERNET` permission via config plugin (privacy signal; revisit if
  we ever add updates/crash reporting).
- **Edge-to-edge is mandatory on Android 16**: audit safe-area insets on every screen
  (RN 0.86 improved e2e support; still verify lists, headers, FAB).

## 6. UI

Three tabs (expo-router): **Rules · Blocked · Settings**, plus modals:
onboarding/permission gate, rule editor, app picker.

- **Rules:** flat list; each row = app scope chip(s), pattern preview in mono type,
  Allow/Deny badge, enable switch, tap-to-edit. Empty state explains the default policy
  in one sentence ("Everything shows. Rules you add can block or require notifications.").
- **Rule editor:** scope picker (All apps / Choose apps) → pattern field (mono font,
  live match indicator via `testPattern`) → case toggle → action segmented control →
  sample test area ("paste a notification to try it").
- **App picker:** search field, app icon + name rows, multi-select with a selection
  counter; sticky "All apps" option at top.
- **History:** unified reverse-chronological feed of every notification the listener
  sees. Each row shows app icon, title preview, disposition badge (Shown / Blocked),
  relative time. Blocked entries include the matched rule ("blocked by `promo.*sale`").
  Shown entries include the reason ("allowed — no rules matched" or "allowed by `<label>`").
  Row actions: restore a blocked entry (re-posts a copy), "allow this app" / "block this
  app" shortcuts (pre-fill a rule). Header: clear all history. Empty state:
  "No notifications yet." The entire feed proves the filter is working.
- **Settings:** default policy (two plain options with a one-line consequence each),
  filter ongoing toggle with honest warning copy, log size, theme (system/light/dark),
  import/export rules (JSON via SAF), "Send test notification" (posts one from our own
  package through the full pipeline), About ("All processing happens on this device.
  Notification content never leaves it.").
- **Permission banner:** if notification access is ever revoked, every tab shows a
  persistent top banner linking back to Settings — the app must never pretend to filter
  while it can't.

### Design system (anti-slop, per the 19-point rubric)
- Neutral zinc scale + **one** deliberate accent (suggest warm amber for 'deny'/blocked
  semantics and keep positive states neutral) — no indigo/violet, no gradients, no glass.
- Phosphor icons, **one weight** (regular), duotone reserved for tab-active only.
- System font; 4/8 spacing scale; one radius scale; borders only where they mean a boundary.
- Dark mode: NativeWind `darkMode: 'class'` driven by setting + system default; body text ≥ 4.5:1.
- Copy rules: concrete verbs, no hype words, no emoji, no exclamation marks. Headings like
  "Blocked today", not "Your Blocked Notifications 🚫".
- Pre-ship pass against the avoid-ai-slop rubric before M5 closes.

## 7. Testing

- **Kotlin JVM unit tests** for the core: `RuleEngine` (deny-overrides-allow, default
  policies, scope matching, field extraction, 4 KB cap, invalid-regex handling) and
  `RuleStore` (serialization round-trip). This is the heart of the app; test it hard.
- **Jest (JS):** rule-form validation, import/export schema, settings reducers.
- **Manual matrix** on your Android 16 device: in-app test notification for allow/deny/
  default-policy combinations; force-stop the app and confirm filtering continues;
  uninstall/reinstall rebind; ongoing-notification skip; edge-to-edge on every screen.
- No Detox in v1 — the special-permission gate makes automated e2e poor ROI here.

## 9. Decisions made

- **Distribution: personal / sideload.** `QUERY_ALL_PACKAGES` is fine (no Play review
  needed); `INTERNET` stripped via config plugin for a clean privacy story.
- **App picker:** shows all installed apps, but the listener service accumulates a set
  of "seen" packages (apps that have actually posted notifications). The picker tags
  these with a subtle indicator and includes a "Only notifying apps" toggle filter.
  This avoids the impossible query (Android doesn't expose POST_NOTIFICATIONS grant
  state to third parties) while still matching the user's intent.
- **Restore in v1:** included — it's a trust feature (seeing what was blocked and
  undoing it). Keeps the blocked log from feeling like a black hole. Needs
  `POST_NOTIFICATIONS` runtime permission; prompt only when user taps restore.
- **Field granularity in v1:** keep the title/text/any selector; compact UI as a
  single-select row (three options, no visual overload).

## 10. Risks

- NativeWind×Tailwind 4×RN 0.86 interplay — verified at M0, fallback to Tailwind 3.4.
- OEM battery killers (Xiaomi/Samsung) may stop the listener process → optional
  "disable battery optimization" prompt + honest troubleshooting copy.
- Catastrophic regex backtracking → 4 KB content cap, document pattern hygiene.
- OTP/sensitive content redaction (Android 15+) limits content matching for those
  notifications by design.

## 11. QoL features for later (post-v1 backlog)

1. **Snooze instead of block** — `snoozeNotification()` exists in the same API; adds a
   third action next to allow/deny.
2. **Quiet hours / schedules** — time-window profiles ("block everything 23:00–07:00
   except rule X"), with a quick tile to pause filtering for 1 hour.
3. **Match-explanation view** — show the exact matched substring in the blocked log
   ("matched `sale|offer` in text") — huge for trust and rule debugging.
4. **Stats** — blocked-per-day and top-offending apps; one compact chart.
5. **Per-channel rules** — `notification.channelId` is visible; filter "Gmail/Promotions"
   without regex.
6. **Rule templates** — canned starting points ("mute promo words", "allow messages
   containing my name") to lower the regex barrier.
7. **Regex helper** — visual builder (contains / starts with / whole message) that
   compiles to the same pattern, plus a cheatsheet screen.
8. **Quick-create from the blocked log** — "always block/allow notifications like this"
   pre-fills a rule from the blocked entry.
9. **Group-summary cleanup** — auto-cancel empty group summaries when all children were filtered.
10. **Backup sync** — rules export/import via a cloud drive folder (still no server of our own).
